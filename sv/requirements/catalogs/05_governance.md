## 1. Purpose

This file defines the governance requirements for MH catalogs as *data*:
the 33 CSV sidecars in this directory as the machine-readable legal basis,
the authority chain (official XLSX workbook, PDF overlay, derived CSVs), the
regeneration procedure on new source versions, the version regime (the v1.1
2026 re-versioning lesson: version numbers are not monotonic and codes get
re-assigned), the module-side dated-storage rule that preserves the meaning
of stored documents' catalog references, and the corrections log.

It does **not** cover: per-type catalog *usage* inside DTE structures and
events — which fields consume which catalog (see
[../e-invoicing/01_document-types.md](../e-invoicing/01_document-types.md),
cluster A1) — event semantics that merely reference codes (A3–A5), or tax
computation rules around CAT-015 (A10, `taxation/`).

## 3. Functional Requirements

### 3.1 Machine-readable authority

- **SV-CAT-FR-001:** The system shall treat the 33 CSV sidecars (CAT-001 through CAT-033, file/row map in [_INDEX.md](_INDEX.md)) as the machine-readable legal basis for every catalog code referenced in DTE generation, validation, and event construction. (LB-001; EVID-086)
- **SV-CAT-FR-002:** The authority chain for catalog data shall be: official XLSX workbook (LB-001) first; official PDF text (LB-002) as overlay only where the workbook is known-incomplete; the CSVs are derived artifacts generated by `shared/scripts/build_catalogs.py` and shall never be hand-edited — every discrepancy against a newer official catalog is resolved by regeneration, not in-place correction. (LB-001; LB-002; LB-006)
- **SV-CAT-FR-003:** Any correction applied during sidecar building (workbook defect, overlay reconciliation) shall be recorded in the corrections log of `_INDEX.md`; a sidecar shall contain no deviation from its source that is not logged there. (LB-006)

### 3.2 Version regime & regeneration

- **SV-CAT-FR-004:** Catalog version numbers shall NOT be treated as monotonic or comparable: the 2026 re-versioning replaced the 2022 v1.2 set with **v1.1** (number went down). Catalog regime identity and supersession decisions shall be keyed by source publication date, never by version-number ordering. (LB-001 vs LB-005; EVID-086; regulatory-change-management)
- **SV-CAT-FR-005:** When a new official catalog source version arrives in `sv/sources/`, the pipeline shall: (a) capture what changed, its effective date, and the adaptation window BEFORE synthesis proceeds against it; (b) re-run `build_catalogs.py` to regenerate the sidecars wholesale from the new source; (c) record the supersession (old version+date, new version+date, per-catalog delta) in `_INDEX.md` and the supersession ledger. Sources already read are never modified. (LB-006; LB-001)
- **SV-CAT-FR-006:** The system shall honor the Cuadro 4 adaptation SLA for catalog changes — structural "Versiones" changes: compliant within the 10 primeros días hábiles of the third month after MH communication; minor "Modificaciones": within the 10 primeros días hábiles of the next month; non-structural: immediate — noting that MH refuses the *sello de recepción* to non-compliant documents after the deadline, so catalog-regime cutover dates are release-gating. (LB-003; EVID-077)

### 3.3 Module-side dated storage

- **SV-CAT-FR-007:** Catalog data in the modules shall be stored as dated rows — (catalog, code, value, valid_from, valid_to) — where a new catalog regime APPENDS rows and closes the previous regime's rows (valid_to), and never replaces a row's value or reassigns a code's meaning in place. (LB-006; regulatory-change-management Q3 adopted here as requirement)
- **SV-CAT-FR-008:** A catalog reference in a stored (posted/sealed) document shall always resolve against the catalog regime in force at that document's date: the v1.1 restructure re-assigned CAT-013 municipio codes under the 44-municipio model (2023 territorial reorganization), so replacing catalog rows in place would silently corrupt the meaning of stored documents. Historical regime rows shall be retained indefinitely. (LB-001; LB-005; EVID-086)
- **SV-CAT-FR-009:** On each regeneration diff, the pipeline shall classify per-catalog changes as: new codes, withdrawn codes (valid_to set), re-assigned codes (same code, different value ⇒ two dated rows, both retained), renamed catalogs, and repurposed/new-scope catalogs; re-assigned and repurposed cases shall be modeled as new regime rows, never as edits. (LB-006; EVID-086)
- **SV-CAT-FR-010:** Migration on module update in a live database shall load new regime rows and close old ones, and shall NOT rewrite existing document references or stored catalog values; no stored document's reported meaning may change as a result of a catalog update. (LB-006; FR-008)

### 3.4 v1.1 new-scope catalogs & code changes

- **SV-CAT-FR-011:** CAT-002 (*Tipo de Documento / Evento*) shall be honored as a single 13-row catalog covering both the 11 DTE type codes and the event codes 17 (*Evento de Operaciones Especiales*) and 18 (*Evento de Retorno*): document-type validation and event `tipoEvento` validation draw from the same catalog, with codes 17/18 valid only as event types. (LB-001; EVID-086; A5)
- **SV-CAT-FR-012:** CAT-008 shall be loaded as the *Distrito* (district) catalog — 263 rows: 262 districts plus code 00 "Otro (Para extranjeros)" — replacing the 2022 regime in which CAT-008 was marked "eliminado"; distrito codes are consumed by DTE emitter/receptor address fields and must correspond to the declared CAT-012 departamento / CAT-013 municipio pair. (LB-001; LB-004 N°28/49; EVID-086)
- **SV-CAT-FR-013:** CAT-013 shall be loaded as the restructured 45-row municipio catalog (44-municipio model plus code 00 "Otro"): the v1.1 codes (e.g. 13/14/15 = Ahuachapán Norte/Centro/Sur) are re-assigned relative to v1.2, and both regimes shall coexist as dated rows per FR-007/FR-008. (LB-001; EVID-086)
- **SV-CAT-FR-014:** CAT-023 shall be loaded as *Operaciones Especiales* (2 rows: 02 FVS reporting, 97 Comprobantes de Control Interno) — its v1.2 meaning (contingency DTE types) is withdrawn; contingency-eligible DTE types are governed by the Normativa Anexos, not by any catalog. (LB-001; R5; EVID-086)
- **SV-CAT-FR-015:** CAT-033 (*Tipo de Régimen*, new in v1.1 — 4 rows: EX-1 Exportación Definitiva, EX-2 Exportación Temporal, EX-3 Reexportación, TA-1) shall be loaded as a new catalog consumed by FEXE `tipoRegimen` (required for goods exports, null for services). (LB-001; LB-004 N°36; EVID-086)
- **SV-CAT-FR-016:** CAT-024 shall be loaded under its renamed label *Motivo del evento* with unchanged values 1/2/3, and CAT-021 under its renamed label *Documentos Asociados* — renames change presentation labels only, not code semantics. (LB-001; EVID-086)

### 3.5 Serving & client/SaaS split

- **SV-CAT-FR-017:** The SaaS core shall be the authoritative server of current-regime catalog data (generation/validation per D2), while the Odoo client holds a local dated cache of catalog rows for capture UX, stored-document display, and offline Tier-A readability; both sides shall apply the same date-keyed regime-selection rule so a code resolves identically on both sides at any document date. (LB-006; ARCH D2/D3)
- **SV-CAT-FR-018:** Catalog data served to the client over the private protocol shall be regime-stamped (source version + publication date), so the client can detect a newer served regime than its cache and refresh without ever mutating already-stored rows. (LB-006; ARCH D2)

## 6. Acceptance Criteria

- **AC-001:** Given the current sources (51_ v1.1 XLSX + 50_ PDF), when `build_catalogs.py` is re-run, then all 33 sidecars regenerate byte-identical to the committed set and `_INDEX.md` row counts match (FR-001, FR-002).
- **AC-002:** Given a hypothetical new official catalog source, when the pipeline regenerates, then every per-catalog delta is classified (new/withdrawn/re-assigned/renamed/repurposed), the supersession is recorded with old and new dates, and no source file is modified (FR-005, FR-009).
- **AC-003:** Given a document stored under the v1.2 regime referencing CAT-013 code 13, when its municipio is displayed or exported after the v1.1 regime is loaded, then it resolves to the v1.2 meaning (not to "AHUACHAPAN NORTE"), and the stored row was never rewritten (FR-008, FR-010).
- **AC-004:** Given CAT-002 code 17, when used as an event `tipoEvento`, then it is accepted; when used as a DTE `tipoDte`, then it is rejected (FR-011).
- **AC-005:** Given a re-assigned code (same code, different value across regimes), when both regimes are loaded, then two dated rows exist, the old row has valid_to = regime switch and the new row valid_from = regime switch, and no code/value pair was overwritten (FR-007, FR-009).
- **AC-006:** Given a structural catalog "Versiones" change communicated by MH, when the third month's 10 primeros días hábiles elapse, then a deployment still generating under the old regime would be refused seal — so the release plan shall schedule cutover before that deadline (FR-006).
- **AC-007:** Given a sidecar that deviates from its source in any way, when `_INDEX.md` is reviewed, then that deviation appears in the corrections log; otherwise the build introduced no unlogged deviation (FR-003).
- **AC-008:** Given a client cache at regime v1.1 and a SaaS serving regime v1.2 (dated later), when the client fetches, then it appends the new regime rows and closes the old ones, and previously stored documents' resolutions are unchanged (FR-017, FR-018).
