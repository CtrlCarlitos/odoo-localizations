## EVID-148 — Certification lifecycle in 5 steps: emisor XML → certificador validates SAT rules + assigns authorization + advanced signature → SAT reception API → acuse per message catalog → certificador stores acuse
- **Loc:** p. 5–6, §I.B "Síntesis del proceso" (Ilustración 1 context)
- **Verbatim:** "1. Cada emisor o contribuyente construye un XML con firma de emisión y lo envía al CERTIFICADOR, quien debe aplicar todas las reglas de validación proporcionadas por la SAT , debiendo retornar al emisor un mensaje de error cuando no se cumplan las validaciones." "2. Una vez validado el mensaje satisfactoriamente por parte del CERTIFICADOR, este asigna número de autorización de forma automatizada y e incorpora la firma electrónica avanzada a la certificación." "3. El mensaje es enviado en formato XML por medio del API de recepción para que SAT proceda a realizar las verificaciones correspondientes, para determinar si el documento es válido o invalido." "4. La SAT devuelve un acuse de recibo con un código de mensaje de respuesta de acuerdo conl catálogo definido y confirmará si el mensaje se rechazó y si se recibió sin errores o con errores." [sic "conl"] "5. El CERTIFICADOR está obligado a almacenar el acuse de recibo de cada DTE enviado, el cual irá firmado por parte de la SAT."
- **Gloss:** Double-validation surface: certificador first applies SAT-provided validation rules (pre-certification), SAT re-verifies on reception. Response vocabulary = "código de mensaje" from the defined catalog (see EVID-159). SAT's acuse is the registration evidence; certificador must store it. Tension: step 5 says acuse "irá firmado", footnotes 6/9 say signature is future (OQ-2).
- **Candidate CRs:** [provider interface] expected response semantics when Odoo (via provider) receives certification results: catalog-coded success/reject/error; store acuse/reference. Error messages returned to emisor when validations fail originate at certificador tier.
- **Topics:** e-invoicing (provider interface); certification lifecycle; mensajes catalog.
- **Doubts/xref:** OQ-2 (acuse signature); mensajes catalog cross-ref EVID-159 and 29_/30_ evidence.

## EVID-149 — Rejection/error handling: responsibility split between certificador and emisor; resend duty when error imputable to certificador
- **Loc:** p. 6, §I.B closing paragraph
- **Verbatim:** "Cuando un documento es rechazado o recibido con errores no imputables al certificador, el certificador tiene la obligación de informar al emisor para su conocimiento y las acciones necesarias; si el rechazo o error es imputable al certificador, este debe corregirlo y enviar de nuevo el documento."

## EVID-151 — Emitter-side DTE composition: DatosEmision minimums per Reglas y Validaciones; Complementos are signed and MUST go to SAT; Adenda must NOT (SAT rejects if present)
- **Loc:** p. 8–9, §II.B, §II.D, §II.E
- **Verbatim:** "En el elemento DatosEmisión el EMISOR consignará los datos de acuerdo con lo establecido en el documento de reglas y validaciones (Documento Reglas y Validaciones)." / "Es el EMISOR el responsable de los datos de emisión, independiente del proceso o sistema empleado la incorporación de la firma electrónica de emisión vincula a la persona que emite el DTE hacia los datos contenidos en el elemento DatosEmision." / "Los complementos deben incorporse conforme con las disposiciones del Régimen FEL y forman parte de los nodos firmados por el EMISOR." [sic "incorporse"] "Cuando existan, los complementos deben ser enviado a la SAT, la SAT verificará y puede rechazar o informar error si un complemento requerido no es enviado." [sic] / "El elemento Adenda no forma parte de los elementos DatosEmision ni DTE, motivo por el cual no se encuentra firmado por el EMISOR ni por el RECEPTOR y no altera la validez de un DTE." ## EVID-154 — Signature technical profile: both signatures are XAdES-BES, RSA, SHA-256, distinct Signature IDs
- **Loc:** p. 13, §II.I (Ilustración 5 context)
- **Verbatim:** "la primera es una firma electrónica simple realizada con un certificado digital que la SAT brindará al contribuyente emisor y la segunda es una firma electrónica avanzada realizada con un certificado digital que el Certificador adquiere con un prestador de servicios autorizado; sin embargo, técnicamente, ambas son incorporadas al XML por medio de un elemento Signature con un ID diferente para la firma de emisión y para la firma electrónica avanzada del certificador, ambas empleando las extensiones Xades-Bes y firmas tipo RSA con algoritmo SHA-256."
- **Gloss:** Legal asymmetry (simple vs avanzada) but ONE technical profile: xmldsig/XAdES-BES, RSA, SHA-256, two Signature elements with different IDs. This is the canonical signing algorithm set for any Odoo-side emisor-signing implementation.
- **Candidate CRs:** emisor signing must be XAdES-BES / RSA / SHA-256 with distinct Signature ID (e.g. FirmaEmisor per XSD id convention); verification of both signatures on received certified DTEs.
- **Topics:** e-invoicing; signatures (XAdES-BES); crypto profile.
- **Doubts/xref:** canonical Signature ID strings come from the XSD (`id="FirmaEmisor"`/`FirmaCertificador`, 29_/30_ EVID-001), not from this doc.

## Product integration-boundary verdict (file-level note)

Everything in this document is SAT↔certificador: the emisor-facing operations ("Cada certificador es responsable de poner a disposición de sus EMISORES una aplicación o servicio", EVID-156; emisor → CERTIFICADOR in lifecycle step 1, EVID-148) sit on the certificador tier. Therefore the Odoo connector's direct contract is the certificador/provider API (TotalDoc), NOT /getToken, /postFactura, /postAnulacionDTE. This document is LB-citable for (a) the semantics the provider must relay (UUID numbering authority, double signatures, message-catalog result codes, acuse evidence, anulación immutability, adenda exclusion) and (b) the SAT-side hooks any provider must satisfy — i.e., requirements the product verifies *through* the provider, plus emisor-side duties Odoo itself owns (DatosEmision construction + XAdES-BES emisión signature, complement/adenda handling, anulación request origination).
